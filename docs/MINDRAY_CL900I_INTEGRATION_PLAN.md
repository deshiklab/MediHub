# Mindray CL-900i integration plan

**Status: discovery only.** The CL-900i is now the proposed first analyzer, but its exact LIS interface, installed software/version, host configuration, facility, and receiving-system contract have not been supplied. MediHub remains synthetic-only: there is no CL-900i adapter, live listener, patient-result model, or real EMS/EMR sender. This document does not authorize a connection.

## What is publicly confirmed

Mindray describes the CL-900i as a fully automated chemiluminescence immunoassay (CLIA) analyzer using an enhanced ALP-AMPPD method, with throughput up to 180 tests/hour, 50 sample positions, and 15 reagent positions. See the [official CL-900i product page](https://www.mindray.com/en/products/laboratory-diagnostics/chemiluminescence-immunoassay/small-test-volume/cl-900i) and [official product brochure](https://www.mindray.com/content/dam/xpace/en/resources/brochure/cl-900i-product-brochure.pdf).

Those public product materials do **not** specify the exact host/LIS protocol and message profile, result-transfer direction, acknowledgement behavior, or the interface available on a particular unit/software release. A separate [Mindray India CLIA article](https://www.mindray.com/in/media-center/blog/understanding-clia-principles-applications/) says bidirectional LIS is available across CLIA analyzers and discusses the CL-900i, but does not identify this unit's protocol or host setup. Do not infer ASTM, HL7, TCP/IP, RS-232, or query/poll support from that general statement.

### Protocol and GitHub reconnaissance

An [unofficial mirror of a CLIA 900 service manual](https://pdfcoffee.com/manual-de-servicio-clia-900-pdf-free.html) claims that the CL-900i can use HL7 or ASTM E1394 over network or serial links. Treat this only as a lead: the copy is not a vendor-controlled contract, and its exact revision/region match to the installed unit is unknown. We still need the Mindray-authorized LIS/host-interface guide and written authorization.

A public GitHub search found generic ASTM libraries but no verified CL-900i driver: [`astmio`](https://github.com/PrasoonPratham/astmio) is an MIT-licensed, pre-release Python E1381/E1394 project; [`python-astm`](https://github.com/kxepal/python-astm) is another generic implementation with no clear SPDX license in repository metadata; [`Mindray-Listener`](https://github.com/coudjo/Mindray-Listener) describes a different Mindray binary protocol and explicitly says it is not ASTM or HL7. None is evidence of CL-900i compatibility, so no third-party implementation has been adopted.

### Audit of the proposed HL7 v2.3.1 and ASTM examples (2026-10-11)

The supplied examples are review material, not an adopted CL-900i message profile. They have not been added to the parser or mapping configuration. Compared with [HL7 v2.3.1 Chapter 7](https://www.hl7.eu/HL7v2x/v231/std231/Ch7.html), [Chapter 2](https://www.hl7.eu/HL7v2x/v231/std231/CH2.html), the [QRD v2.3.1 field definitions](https://hapifhir.github.io/hapi-hl7v2/v231/apidocs/ca/uhn/hl7v2/model/v231/segment/QRD.html), and the relevant [ASTM/CLSI interface layering](https://www.bdbiosciences.com/content/dam/bdb/marketing-documents/products-pdf-folder/software-informatics/bd-facs-workflow-manager/BD-FACS-Workflow-Manager-Software-LIS-Interface-Specification-Guide_V1.1.pdf), the following points need correction or vendor confirmation:

- **The query pair is for observations, not proof of a worklist/order query.** HL7 v2.3.1 labels QRY^R02 / ORF^R04 “query for results of observation” / response transmitting requested observations. That pair does not, by itself, define a barcode-triggered test-order or worklist lookup, much less prove that the installed CL-900i supports one. The official [Mindray Patient Data Share guide](https://www.mindray.com/content/dam/xpace/en_us/service-and-support/training-and-education/resource--library/technical--documents/operators-manuals-1/H-0010-20-43061-2-Mindray-Patient-Data-Share-Protocol-Programmers-Guide-v14_2-03-2020.pdf) uses QRY^R02 / ORF^R04 for solicited bedside-monitor data; that is a different product/interface. An ORU^R01 is the standard unsolicited observation-reporting pattern, but it too is only a generic candidate until Mindray supplies the CL-900i profile.
- **The QRD explanation conflicts with both standard field meanings and the example.** QRD-2=`R` means record-oriented response format; QRD-3=`I` means immediate priority. QRD-8 is the repeating *Who Subject Filter* (XCN), and QRD-9 is the repeating *What Subject Filter* (CE)—they are not “real-time” and “barcode” fields by definition. In the pasted segment the barcode-like value is placed in QRD-8 while the prose says QRD-9 contains it. A local vendor profile could define a specific query convention, but the supplied text is internally inconsistent and cannot be used to select a field safely.
- **`ORC-1=NW` is order control, not a results-only status.** HL7 defines `NW` as a new order. Although an ORC group can appear in some observation-query responses, the sample's use of `NW` needs an explicit explanation from the authorized profile and receiver. MediHub's approved first scope excludes creating, sending, or requesting orders/worklists; do not translate this code into order traffic.
- **Analyzer completion is not technician verification.** In HL7 v2.3.1, OBX-11 `F` is final and verified; `R` is entered but not verified, and `P` is preliminary. Do not forward or interpret source `F` as permission to mark the destination result verified, final, or released. Preserve the source status and use only a receiver-approved pending/review state that keeps lab-technician verification explicit. If the destination cannot hold a result for review, stage it for an authorized technician rather than submitting it as final.
- **One result example is internally inconsistent.** The example gives value `2.45`, reference interval `0.27-4.20`, and OBX-8 flag `H`; 2.45 lies within the stated interval, so the high flag does not agree with the example as written. Treat mismatched value/range/flag combinations as a validation hold, not as a reason to auto-correct or reinterpret the result.
- **The ASTM standard names mix record content and framing.** ASTM E1394-97 corresponds to the high-level LIS02-A2 record/message-content layer; ASTM E1381 corresponds to the low-level LIS01-A2 framing/transport layer. The supplied “E1394 / LIS01-A2 character-frame” label therefore conflates layers. Its STX/frame-number/payload/ETX-or-ETB/checksum sketch is not, by itself, a complete framed session. If the approved CL-900i profile uses LIS01/E1381 framing, validate its session control (ENQ/ACK/NAK/EOT), sequencing, timeouts, retransmission, checksum, and multi-frame behavior against that revision. The current Python scaffold remains record-level only and is not an E1381 transport implementation.
- **Custom flags and actions remain unverified.** The proposed ODR/EXP/CAL/OSD/SUB/INS/ABS and `<`/`>` meanings, plus any dilution/repeat actions or numeric ranges, are not established by the public sources reviewed or an authorized, version-matched CL-900i guide. Keep raw codes and values; do not map them to clinical meaning or trigger actions until Mindray and the facility approve the exact dictionary and workflow.

**Disposition:** do not adopt these samples as the CL-900i profile or add query, order, worklist, analyzer-control, automatic verification, or release behavior. Keep development synthetic-only and results-only. Revisit message selection, field positions, result-state mapping, framing, flags, and ACK behavior only after obtaining the exact installed interface version, an authorized Mindray profile, and receiver approval.

### Review of the follow-up HL7/ASTM template

The newly supplied “reference template” still has no controlled Mindray document number/revision or installed CL-900i software/interface version. It is therefore another candidate to audit—not proof of this unit's host profile—and has not been put in parser configuration or fixtures.

- **HL7 barcode position is wrong in both the comment and the sample.** Splitting the supplied OBR line on `|` places `BARCODE_123456` in **OBR-16**, not OBR-15. In v2.3.1, OBR-15 is *Specimen Source* (CM) and OBR-16 is *Ordering Provider* (XCN). The comment calls OBR-15 a barcode field, but that is not its standard name/type; the sample actually puts the barcode-like value in the ordering-provider slot. Use only the exact vendor/receiver-defined specimen or accession identifier field—do not shift it by guesswork. See [HL7 v2.3.1 Chapter 7](https://www.hl7.eu/HL7v2x/v231/std231/Ch7.html) for the OBR field definitions.
+- **The result is still marked verified/final.** The sample uses both OBR-25=`F` and OBX-11=`F`; in v2.3.1, OBR-25 `F` means final results stored and verified, while OBX-11 `F` is final. Neither may bypass lab-technician verification or mark/release the receiver result as verified. Preserve the source values and use only a receiver-approved pending/review state; otherwise stage for an authorized technician. See [HL7 Chapter 7](https://www.hl7.eu/HL7v2x/v231/std231/Ch7.html).
+- **The `H` flag conflicts with the example's own value/range.** `2.45` is inside `0.27-4.20`, so OBX-8=`H` is inconsistent as written. Quarantine/hold such a mismatch; don't auto-correct or reinterpret it.
+- **The sample's processing ID says production.** MSH-11=`P` denotes production, but the message uses sample/test identities. Do not send this fixture to a production receiver. Use a test processing ID only with an approved non-production route; MSH-11 alone is not a safety control. See [HL7 Table 0103](https://www.hl7.eu/HL7v2x/v231/std231/CH2.html).
+- **ORC-1=`RE` is not a generic “result upload” status.** Its standard meaning is “observations to follow.” HL7's v2.3.1 guidance says it is required in ORM for an order followed by observations, but is not necessary in ORU because the OBR/OBX structure already carries the result. Its use in this ORU must match the receiver profile; it does not establish bidirectional order/worklist behavior. See [HL7 Chapter 4](https://www.hl7.eu/HL7v2x/v231/std231/CH4.html).
+- **The ASTM title conflates record content and transport, and the shown frames are incomplete.** E1394-97 is the record-content layer (LIS02-A2); E1381/LIS01-A2 is the low-level framing/session layer. The diagram omits ETX/ETB, checksum, and session control such as ENQ/ACK/NAK/EOT, so it is not a complete E1381 exchange. Validate the exact framing variant, checksum, retries, timeouts, and session behavior against the authorized unit-specific guide. The current scaffold still parses de-framed records only. See the [generic ASTM record field reference](https://python-astm.readthedocs.io/en/0.4.1/records.html) and [CLSI/ASTM interface guide](https://www.bdbiosciences.com/content/dam/bdb/marketing-documents/products-pdf-folder/software-informatics/bd-facs-workflow-manager/BD-FACS-Workflow-Manager-Software-LIS-Interface-Specification-Guide_V1.1.pdf).
+- **ASTM R-record comments use inconsistent field numbering.** With the E1394 field numbers (including the record-type field), the shown R record has test ID at R-3, numeric value at R-4, abnormal flag at R-7, and result status at R-9. The comments label value as field 3 and flag as field 6, effectively counting after the record-type field; elsewhere the O-record comments count the record type (O-3 specimen ID, O-5 test ID). Use one documented numbering convention throughout. The O-record example's barcode at O-3 and test ID at O-5 are consistent with the standard numbering; the R-record annotations are not.
+- **The assay code list is still a site/device dictionary, not a standard mapping.** `001`/`002`, `TSH`/`FT4`, and `MindrayCode` need confirmation against the exact software version and facility mapping. Keep unknown code/unit/status values opaque; don't normalize or act on them yet.

**Disposition for this follow-up:** no implementation change. The ORU example is a generic unsolicited-results shape, not proof the CL-900i sends it; its “bidirectional” heading is not evidence of a supported order/worklist exchange. Keep results-only scope, technician review, synthetic-only data, and no live transport until the controlled profile and receiver workflow are approved.

### Review of the analytical-driver connection checklist and flag map

The checklist is useful as a list of questions for discovery, but it mixes generic standards, site-specific engineering choices, unverified CL-900i settings, and clinical actions. It is not a controlled interface profile or safe installation procedure. No network values, flag mappings, JSON rules, or live test steps below are adopted in MediHub.

#### Physical and network setup

- **Cable, serial adapter, and endpoint topology need unit-specific confirmation.** RJ-45 and RS-232 may be available on a particular setup, but the correct port, NICs, cable/pinout, serial parameters, and host-versus-workstation path must come from the authorized guide for the installed unit. A null-modem cable is not a universal serial prescription; do not connect a USB-to-serial adapter or change cabling without the approved pinout and facility biomedical/IT review.
- **The client/server role is a discovery item, not a universal rule.** An [unofficial CL-900i service-manual mirror](https://pdfcoffee.com/manual-de-servicio-clia-900-pdf-free.html) says the analyzer acts as a TCP client by default and the LIS as server, and describes configurable network/serial connections. This is only a lead: it is not a controlled Mindray interface document, and it does not establish the role or topology for the installed software. The same source does not validate the checklist's example ports (`5100` or `9100`) as CL-900i ports. Obtain the exact vendor-approved role, interface address, listener port, and whether an existing LIS already owns the connection.
+- **Do not open a broadly “bidirectional” firewall path.** The facility network owner must approve the exact source, destination, protocol, and port for the confirmed connection mode, with least-privilege rules and stateful return traffic as appropriate. Do not copy example ports or expose a whole subnet. Static assignment or a DHCP reservation must follow the facility address plan; “outside the DHCP range” alone does not prevent collisions.
+- **Ping is not an interface acceptance test.** ICMP reachability from the LIS toward the analyzer does not prove that the analyzer can open the intended TCP session, that a listener is reachable, or that HL7/ASTM framing and acknowledgements work; ICMP may also be filtered by policy. Test only the approved path at network, transport, framing, and application layers in an authorized non-production environment.
+- **The `≥1500 VA` UPS figure is unsupported as a CL-900i requirement.** The existing plan records public regional brochures with differing analyzer ratings (500 VA and 1000 VA); neither establishes a complete workstation/network load or required runtime. Size any UPS from the exact local nameplates, workstation/peripheral loads, required runtime, and facility biomedical/electrical standards—not this unreferenced blanket threshold.

#### Protocol and framing details

- **HL7 and ASTM are candidates, not a confirmed protocol selector.** The exact installed CL-900i software, host-interface revision, direction, message profile, and lower-layer transport are still unknown. HL7 v2.3.1 or ASTM E1394-97 cannot be selected solely because the checklist lists them.
- **The HL7 delimiter list is incomplete and should not be hard-coded as “defaults.”** HL7 messages declare the field separator in MSH-1 and encoding characters in MSH-2. The conventional v2 set is `|` plus `^~\&`; the checklist omits `&` (the subcomponent separator). Parse the declared characters or implement the exact authorized profile. If HL7 runs over TCP, also obtain the message-boundary/framing rule (such as MLLP or a vendor-specific wrapper); TCP itself is a byte stream. See [HL7 v2.3.1 Chapter 2](https://www.hl7.eu/HL7v2x/v231/std231/CH2.html).
+- **ASTM ACK/NAK byte values are not a complete handshake.** ACK=`0x06` and NAK=`0x15` are standard control bytes, but timing alone is insufficient. The approved E1381/LIS01 variant must specify ENQ/EOT session control, STX/ETX/ETB framing, checksum scope/encoding, frame sequence, per-frame acknowledgements, contention, timeout, retry, and disconnect behavior. A link/frame ACK is not clinical acceptance, verification, or release. The existing parser remains de-framed-record-only.

#### Mappings, flags, and patient context

- **Barcode and assay mapping are not implementation-ready.** The checklist repeats the incorrect HL7 OBR-15 barcode claim: OBR-15 is Specimen Source, not a barcode field; the prior supplied line placed its barcode-like token at OBR-16, which is Ordering Provider. ASTM O-3 is the standard Specimen ID position, but that does not prove the CL-900i uses it as a receiver accession. Confirm specimen/accession identity fields, code dictionary, channel mapping (`001`/`TSH`, `002`/`FT4`), allowed units, precision, and receiver association rules from the controlled profile and receiving-system contract. Preserve source value/unit and transformation provenance; never silently convert units or match a patient from a barcode without the authoritative accession/order workflow.
+- **The proposed flag meanings and automation rules are unverified and clinically unsafe to configure as written.** No authorized, version-matched dictionary establishes `>`, `<`, `ABS`, `ODR`, `INS`, `EXP`, `CAL`, `OSD`, or `SUB` with the stated meanings (such as PMT saturation, clot, expired reagent, calibration failure, or substrate/temperature fault). Do not infer dilution, rerun, cancellation, suppression, severity, or release actions from these labels. In particular, “clear `<` for release” and JSON `block_release: false` conflict with MediHub's explicit no-auto-release boundary. Preserve the raw code/value, hold unknown or inconsistent status for technician review, and do not command analyzer actions.
+- **The table and JSON are internally inconsistent even before vendor validation.** The reagent status is named `REAGENT_EXPIRED_WARNING` in the table but `REAGENT_EXPIRED_WARN` in JSON; optical status is `OPTICAL_HARDWARE_ERROR` versus `OPTICAL_HARDWARE_ERR`. The table says `INS` cancels test execution and `SUB` prevents rerun, while the JSON only sets `block_release` and does not encode those actions. These discrepancies reinforce that the JSON must not be copied into a driver, mapping file, or receiver configuration.
+- **Demographic exchange is outside the approved first scope.** PID and ASTM P records carry patient information, but their presence in a generic profile does not authorize real-time patient queries or bidirectional demographics. Do not request or send demographics, patient records, worklists, or orders in this results-only intake.

#### Proposed live-loop tests

- **Test 1 must not write a live result directly to a patient chart.** A manually programmed analyzer result can lack a validated order/accession association. Until separate approvals exist, exercise only synthetic fixtures/simulators and the synthetic receiver. Any later approved pilot must first confirm that the named receiver can hold an unverified result for lab-technician review; analyzer `F` or a transport ACK must not finalize it.
- **Test 2 describes the wrong standard query for a worklist.** HL7 v2.3.1 defines QRY^R02 / ORF^R04 as a query/response for results of observation; ORF is an observational report, not a generic order response or worklist-layout message. It does not prove that the analyzer can query test orders or automatically select assays. Such order/worklist behavior is expressly out of scope. See [HL7 v2.3.1 Chapter 7](https://www.hl7.eu/HL7v2x/v231/std231/Ch7.html).
- **Test 3 must not inject an assumed `ODR` clinical meaning into a live unit.** In synthetic tests, verify raw-code preservation, mismatch quarantine, and that technician review is required; do not trigger dilution, rerun, suppression, or release. Any future physical test needs Mindray and facility approval, the exact controlled profile, an approved non-production route, and an agreed test procedure.

**Disposition for this checklist:** retain it only as a discovery prompt. Do not implement its port/IP/UPS values, flag JSON, patient-demographic exchange, QRY/ORF worklist loop, or production tests. MediHub remains synthetic-only and results-only, with no orders/worklists, analyzer control, automatic verification, or release. Any Bangladesh pilot still requires separate facility/Mindray approval, the exact receiver contract, and applicable local privacy, security, and deployment review.

The site-preparation values are a separate installation concern. ## User-confirmed workflow and proposed safe data path

The requested topology is for MediHub to read results directly from the CL-900i and make them available to lab technicians in the facility's EMS/EMR/HMS for verification. The initial scope is results-only: MediHub must not send worklists, orders, assay controls, or analyzer configuration changes. This records the desired workflow; it does not confirm that the unit's installed LIS mode supports it.

```text
CL-900i
  └─ vendor-supported LIS interface (protocol and direction: TBD)
       └─ MediHub lab ingress adapter (initial scope: results only, read-only)
            └─ frame/message validation and protocol parser
                 └─ typed lab-result event preserving source data and status
                      └─ accession/order and patient-context verification
                           └─ reviewed assay/code/unit mapping and quarantine
                                └─ durable outbox with stable idempotency key
                                     └─ the named LIS / interface engine / EMR / EMS
                                          (only via its approved receiver contract)
```

The requested source is the analyzer itself. Before opening a direct connection, the facility and Mindray must confirm the approved host mode, whether the CL-900i is already connected to an LIS, and whether it permits another host. Do not interrupt an existing LIS or create a competing connection. If direct access is not permitted, the fallback is an approved read-only export/API from the existing LIS.

“Pull” needs a device-specific decision: completed results might be pushed by the analyzer, requested by an authorized host, or exposed through the LIS. Even when the analyzer initiates a result upload, MediHub can receive it without sending orders. Use the least-permissive vendor-supported **results-only** mode. Do not download worklists, send orders, change analyzer configuration, start/stop assays, or issue other control commands in the first integration.

## Data and workflow requirements

The current `ObservationEvent` accepts only a numeric scalar, and the current FHIR R4 mapper and receiver are synthetic-only. A laboratory integration needs a separately reviewed result model before a live parser is written. The exact fields must come from the authorized interface guide and facility workflow; at minimum, assess:

- analyzer identity/model/software version and source message/result identifiers;
- specimen/accession and order identifiers, sample type, assay/test code, raw result value/text, original unit, and result timestamp;
- result lifecycle (for example, preliminary, verified/final, corrected, repeated, or cancelled), analyzer flags, dilution/repeat details, and any reference/interpretation fields actually supplied;
- source code/unit and any proposed normalized code/unit, with a reviewed, versioned mapping and a traceable reason for every conversion.

Preserve the source result, code, unit, status, and timing. Do not guess an assay mapping, convert units, round values, infer a reference range, or turn an analyzer flag into a clinical interpretation. Unknown or inconsistent codes/units/statuses, duplicate/correction ambiguity, and missing association data must be quarantined for authorized review—not silently forwarded. Define separately how QC, calibration, maintenance, and non-patient records are recognized so they cannot be mistaken for patient results.

Associate a result using the facility-authoritative accession/order and patient-context workflow. Do not match by patient name, bed/location, timing, or analyzer/sample position alone. The requested technician review must remain explicit: deliver only as draft/preliminary/unverified if the receiver supports that workflow; otherwise stage the imported result for an authorized lab technician before any EMR submission. MediHub must never mark a result verified/final or auto-release it. An analyzer transmission acknowledgement is not clinical verification or EMR acceptance.

## Destination contract

The user uses EMS/EMR/HMS to mean the facility's Electronic Medical Record / Medical Record Management / Hospital Management Software. The exact vendor, product/version, and API are still unknown. Confirm whether the actual receiving endpoint is that system, an LIS, or an interface engine, and whether it accepts a pending/unverified result for lab-technician review. Obtain the approved interface contract before choosing a sender:

- **HL7 v2:** exact version/profile, required ORU message structure (or other agreed message), transport/framing, ACK/NAK meaning, correction/replacement rules, duplicate key, retry policy, and sandbox procedure.
- **FHIR:** exact server/version, CapabilityStatement, accepted profiles/resources (often a coordinated DiagnosticReport/Observation/Specimen/ServiceRequest workflow), identifiers, authorization/scopes, response/ACK meaning, idempotency, and correction behavior.

These are alternatives to evaluate against the real receiver contract, not assumptions about what a particular Bangladesh EMS/EMR accepts. The current generic synthetic FHIR R4 Observation is not a production sender, Bangladesh Core conformance claim, or facility integration.
