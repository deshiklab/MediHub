Important scope: This guide describes the local synthetic preview only. It is not a clinical product, a live device connector, or an EMR/EMS integration. Use generated demo data only; never enter patient details, real measurements, credentials, or live endpoints.

1. What MediHub does in this preview

MediHub demonstrates a local, synthetic device-to-ingestion-to-outbox workflow. The app generates arbitrary sample values, keeps curated event and delivery metadata for the running process, and sends test deliveries only to an in-process receiver. No physical device, remote service, facility system, or patient record is contacted.

  • Safe for: product walkthroughs, software development, mapping exercises, and test-flow demonstrations with synthetic values.
  • Not for: diagnosis, treatment, clinical monitoring, production operations, real patient information, or live integration configuration.
  • Most workbench changes and registrations are temporary in-memory drafts and reset when the server restarts.

2. Operations overview

  1. Open Operations to review the synthetic source and in-process receiver status.
  2. Read the metric cards for generated events, duplicate replays, delivery attempts, acknowledgements, pending work, and policy holds.
  3. Review recent events, outbox activity, policy holds, and curated audit actions. Event identifiers are shortened in the table.
  4. Use Inspect on a delivery to view its allowlisted synthetic details. A terminal synthetic failure can be manually retried when the control is enabled.

A displayed “healthy” state describes only the local demo components; it is not a facility or device health signal.

3. Device management

  1. Open Device management and choose Register simulator to add a demo device to the running process.
  2. Use Set active or Set inactive to control whether that simulator can emit demo samples. These controls never operate hardware.
  3. Select a simulator and choose Emit sample to run a synthetic sample through the local pipeline. Inspect the per-device flow for source, ingestion, outbox, and test-sink stages.
  4. The catalog contains illustrative device categories only. Selecting one prepares a non-secret draft; it does not verify compatibility or configure an API.
  5. Use the export controls to download up to 12 recent, curated synthetic rows as CSV or JSON. Treat the files as test artifacts and do not add real information.

The device API form accepts only non-secret draft metadata. Endpoint, authentication, hardware discovery, and real device API calls are intentionally unavailable.

4. Mapping drafts and tests

  • Add an exact source metric and unit to a mapping draft. Identity rules preserve the synthetic scalar; linear rules apply the configured scale and offset, with the requested decimal precision.
  • Use Preview mapping with a selected simulator and synthetic value to check a match. A missing exact code/unit match should remain unmapped rather than being guessed.
  • Golden test vectors capture synthetic inputs and expected normalized outputs. Run the tests after changing a draft; passing tests are not clinical validation or approval.
  • Revision history is temporary and lets you compare or restore a prior version as a new inactive draft. Mapping activation remains disabled.

5. EMR / EMS API workbench

The cards describe planning targets, not available integrations. FHIR R4 / EMR and HL7 v2 / interface-engine / EMS connection controls are locked; the app has no network sender, endpoint form, credential store, or live activation.

Before any separate real deployment is designed, the responsible facility and authorized technical teams must agree on the interface contract, message and resource profiles, patient-context rules, acknowledgement and idempotency behavior, security controls, test environment, and operational ownership. Do not paste production URLs, tokens, keys, or connection details here.

6. Bangladesh deployment considerations

Bangladesh is a required deployment context for MediHub planning, but this demo is not ready for deployment in a Bangladeshi facility. A future implementation needs local clinical and technical discovery, facility approval, an assessment of applicable Bangladesh laws and regulator guidance, data-residency and hosting decisions, language/accessibility review, and a documented security and privacy assessment.

Validate the exact device models, facility workflows, terminology, units, connectivity constraints, support arrangements, and approved synthetic test endpoint with each participating facility. No local legal, regulatory, or interoperability approval is implied by this preview.

7. Privacy and safety

  • Use only the arbitrary values generated by the simulator. Do not enter names, identifiers, dates of birth, contact details, clinical notes, real readings, or other personal or health information.
  • Do not add credentials or secrets. Do not interpret demo events, mappings, delivery receipts, or status indicators as clinical or production evidence.
  • Exports are created in your browser from recent synthetic rows. Store and share them only as non-sensitive test artifacts.
  • The preview is not a production control plane: it does not provide authenticated operator roles, facility scoping, durable configuration management, or production-grade audit controls.

8. Troubleshooting

  • No sample appears: confirm that a simulator is registered and active, then select it and emit a sample. Refresh the device flow.
  • Mapping preview has no match: compare the source metric code and unit exactly with a draft rule; check the selected simulator and add a synthetic test vector.
  • Delivery is queued or failed: inspect the delivery and its attempts. Use manual retry only when enabled; retries remain local to the synthetic receiver.
  • Changes disappeared: simulator and mapping setup is held in process memory and resets on server restart.
  • Page data looks stale: the operations view refreshes automatically. Reload the page if the browser has lost its connection to the local demo server.

9. Glossary

  • Synthetic: generated demonstration data that does not represent a person or a real device reading.
  • Outbox: a local record of a delivery intent and its attempts; the demo receiver runs in the same process.
  • Idempotency: handling a repeated event identifier without creating a second test receipt.
  • Mapping draft: an inactive, temporary rule for converting an exact synthetic source code/unit to an example normalized code/unit.
  • FHIR R4 / HL7 v2: standards named as future planning targets only; neither is connected in this preview.
